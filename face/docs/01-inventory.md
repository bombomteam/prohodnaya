## Камера (задняя камера iPhone 16 Pro)

Айфон здесь — только замена IP-камеры с RTSP, которой на хакатоне нет. Поэтому он работает как камера-стример, а не как браузер.

**Как устроено сейчас (тестовый стенд камеры, `face/tools/camera/`):**

- На айфоне приложение **Larix Broadcaster** (бесплатное). Оно публикует видео задней камеры по SRT (UDP 8890) или RTMP (TCP 1935).
- На сервере работает **MediaMTX** (MIT) в Docker, вне `compose.yaml`: `run_mediamtx.sh`.
  - Публикация — только с паролем, пароль хранится в `~/.config/prohodnaya/`, не в репозитории.
  - Чтение RTSP (`rtsp://127.0.0.1:8554/gate`) и API — только с самого сервера.
  - Каждая публикация пишется отдельным файлом в `~/face-data/stream/gate/`.
- Порт 1935 на `195.209.220.254` доступен из интернета: проверено с трёх внешних узлов check-host.net, 40–100 мс. Входящий трафик на сервере не фильтруется (`iptables INPUT ACCEPT`). Исходящий адрес сервера другой (`178.105.178.176`), на нём порт закрыт: камеру настраиваем на `195.209.220.254`.
- Замер потока: `probe_stream.py` (OpenCV 5.0 + FFmpeg) печатает только числа: разрешение, кадры в секунду, интервалы, загрузку CPU на декодирование. Кадры не сохраняет.

Замеры с айфона (Larix → RTMP → MediaMTX → `probe_stream.py`, 2026-10-10):

| Параметр | Факт |

| Разрешение и ориентация | 1280×720, альбомная: так шло, пока настройки Larix не применились. 1920×1080 портрет — проверить на роликах |

Вывод: поток с айфона доходит стабильно, 30 к/с. Декодирование почти ничего не стоит (0,12 ядра). Узкое место будет в анализе кадров, а не в приёме.

**Браузерный вариант** (`face/tools/capture/`: страница Safari шлёт JPEG-кадры по HTTPS POST, плюс запись ролика через MediaRecorder) сделан и проверен локально. С айфона не замерен:

- Safari даёт камеру только по HTTPS, а стенд на HTTP;
- временный туннель Cloudflare отвечал 530 на большинство запросов (и по QUIC, и по HTTP/2);
- localhost.run работал, но кадр 150 КБ шёл 1,7 с (~87 КБ/с), это меньше 1 кадра в секунду.

Оставляем вариант как запасной для одиночного снимка.

## Передача видео: сравнение и выбор

| Способ | Время на нас | Что меняется у фронта и бэкенда | Можно ли подменить кадры |
| --- | --- | --- | --- |
| **А. Стример на айфоне (SRT/RTMP) → MediaMTX → модуль читает RTSP** | ~30 мин: медиасервер уже работает, в модуле — чтение RTSP и буфер кадров | Фронт камеру не трогает. Бэкенд вызывает модуль «проверь человека X на камере C за окно попытки». В `compose.yaml` — сервис медиасервера с открытым портом приёма | Через браузер — нет: кадры идут мимо браузера. Можно опубликовать чужой поток, только зная пароль публикации. Перед камерой можно показать фото или экран — это ловит «живость» |
| Б. Страница Safari шлёт JPEG-кадры по HTTPS (POST или WebSocket) | ~40 мин модуль + правка фронта (`environment`, цикл кадров) + приём кадров на бэкенде | Фронт снимает и шлёт кадры, бэкенд проксирует их в модуль | Да: контролёр с инструментами разработчика может слать любые JPEG. Ловим только проверками модуля |
| В. WebRTC из Safari на сервер | > 1,5 ч: сигналинг, STUN/TURN, `aiortc` | Фронт — WebRTC-клиент, бэкенд — сигналинг | Да: дорожку в браузере можно подменить |
| Г. Своё iOS-приложение | Не успеваем: подпись, сборка | — | — |

**Рекомендация: А.** Это та же схема, что с настоящей IP-камерой: на объекте вместо айфона подставляется RTSP-адрес камеры, остальное не меняется. Распознаёт сервер, а браузер контролёра не участвует в передаче кадров. Запасной вариант — одиночный снимок через фронт, как сейчас (`faceImage` → бэкенд → модуль): это «видео из одного кадра».

**Как кадры связываются с попыткой прохода:**

1. Модуль постоянно читает поток камеры C. Берёт 4 кадра в секунду и по каждому считает людей, находит лицо, оценивает качество, считает эмбеддинг и «живость».
2. Результаты хранятся в памяти за последние ~15 с, с временем прихода по часам сервера. На диск ничего не пишется.
3. Рабочий предъявляет подтверждение с телефона. Бэкенд проверяет подпись и вызывает модуль: «проверь человека X (эмбеддинг эталона) на камере C за окно [начало попытки; подтверждение + запас на задержку потока]».
4. Модуль дожидается кадров до конца окна и возвращает факты:
   - максимальное число людей в окне;
   - лучший кадр и сходство с эталоном;
   - «живость» по нескольким кадрам;
   - причину, если что-то не так.
5. Решение о проходе принимает бэкенд.

Время — серверное, не клиентское. Задержку «камера → сервер» учитываем запасом в конце окна.

## Что нужно от фронта и бэкенда (передать через человека)

- **Фронт (проходная):** для основного режима камера не нужна, видео идёт со стримера. Запасной режим «снимок» остаётся как есть, но с `facingMode: "environment"`. Желательно показывать контролёру живой просмотр с рамками (страница модуля через бэкенд).
- **Бэкенд:**
  - при попытке прохода вызывает `verify` модуля с `camera_id` и окном времени (контракт — `face/docs/api.md`, этап 4);
  - хранит эмбеддинг эталона и версию модели;
  - старый путь с `faceImage` оставляет как запасной.
- **Инфраструктура (`compose.yaml`):**
  - сервис медиасервера MediaMTX: наружу только порт приёма (1935/tcp или 8890/udp) с паролем публикации, RTSP — только во внутреннюю сеть;
  - модулю — адрес потока в переменной окружения.

## Открытые вопросы

- HTTPS для стенда нужен только запасному режиму «снимок» в Safari. Основной режим (стример) без него работает.
- Какой порт приёма открываем на стенде: SRT 8890/udp (меньше задержка) или RTMP 1935/tcp (проще). Решим по замерам.
- Есть ли принтер для теста распечатки.
