## Этап 1. С чем работаем → `face/docs/01-inventory.md`

1. **Сервер.** Подтверди командами (не переписывай на веру) то, что важно для работы моделей: CPU и его инструкции, RAM, свободный диск, GPU и драйвер, работает ли GPU в Docker. Ожидаемо: 16 vCPU Xeon Cascade Lake (AVX-512, VNNI), 62 ГБ RAM, ~107 ГБ свободно, NVIDIA A10 24 ГБ, драйвер 615.71 (CUDA ≤ 13.4).
2. **Камера (видео).** Сделай тестовую страницу камеры в `face/tools/capture/`: задняя камера через `getUserMedia`, кадры видео (3–5 в секунду) уходят на сервер, плюс режим «записать ролик» в `~/face-data/`.
   - Открой её с айфона через временный HTTPS-туннель, например `cloudflared tunnel --url http://localhost:<порт>` (без регистрации). Бинарник туннеля держи вне репозитория, в `~/bin/`.
   - Запиши фактические параметры: разрешение, сколько кадров в секунду реально доходит, размер кадра, задержка, ориентация, какая линза снимает (широкая или сверхширокая — видно по искажениям).
   - Правила туннеля: только на время тестов, только тестовые данные, порты стенда и `compose.yaml` не трогать, после съёмки закрыть.
3. **Данные.**
   - **Пакет кейса:** подтверди состав. Ожидаемый результат для каждого кадра пакета (совпадение / непригодный кадр / подмена) запиши в `face/eval/labels.csv`. Это разметка теста, а не логика модуля.
   - **Съёмка участников команды на айфон** (с согласия), всё только в `~/face-data/`. Нужны эталон и короткие ролики «подхожу к проходной». Плюс негативы: фото и видео на экране телефона, распечатка, двое в кадре, профиль, каска или капюшон, свет сзади. Съёмку можно вести параллельно с этапами 2–3.
4. **Передача видео.** Сравни варианты: страница камеры в Safari шлёт кадры по HTTPS (POST или WebSocket); видеопоток WebRTC; приложение-стример на айфоне (RTMP/SRT) → медиасервер. Для каждого — 2–3 строки: сколько времени займёт, что меняется у фронта и бэкенда, можно ли подменить кадры. Порекомендуй один с учётом срока 3 часа. Как связать кадры с попыткой прохода: бэкенд просит модуль проверить человека X по кадрам за время попытки.
5. **Итог:** таблица фактов, выбранный способ передачи видео, что нужно от фронта и бэкенда, открытые вопросы.

## Этап 2. Задачи из кейса → `face/docs/02-tasks.md`

Из требований и сценариев атак в `face/AGENTS.md` составь задачи четырёх уровней:

- **Обязательно** — иначе провал допуска или снятие;
- **Желательно** — баллы блока «Надёжность прохода»;
- **Если останется время**;
- **Не делаем** — с причиной.

Для каждой задачи укажи: что делаем, какое требование или атаку закрывает, как проверим, сколько времени займёт. «Обязательно» и «Желательно» вместе должны влезть в этап 4. Защита от подмены лица — обязательна (решение команды).

Отдельно реши:

- как считать людей: по лицам или детектором людей (на проходе человек может стоять спиной);
- какие причины отказа возвращаем: код и человеческий текст.

## Этап 3. Выбор стека → `face/docs/03-stack.md`

Кандидаты — стартовая точка, не догма:

| Что | Плюсы | Минусы |
| --- | --- | --- |
| InsightFace: детектор SCRFD + ArcFace (`buffalo_l`), onnxruntime | Высокая точность | Веса только для некоммерческих исследований — риск для журнала решений |
| OpenCV: YuNet + SFace (`cv2.FaceDetectorYN`, `cv2.FaceRecognizerSF`) | Лёгкий, нужен только OpenCV, лицензии MIT и Apache 2.0 | Точность ниже |
| Антиспуфинг: MiniFASNet (Silent-Face-Anti-Spoofing, Apache 2.0) или аналог + проверка движения по нескольким кадрам | Работает по кадрам видео | Проверить на роликах с айфона: экран и распечатка |
| Подсчёт людей: детектор людей | Видит и стоящих спиной | Лицензия: Ultralytics YOLO — AGPL-3.0, это риск; есть варианты с Apache 2.0 |

Не тратить время: dlib и face_recognition (у них известны ложные совпадения у азиатских лиц, а у нас пара Кимов), облачные API (запрещено), обучение своих моделей.

Что сделать:

1. **Один скрипт оценки** в `face/eval/`. Прогони **2 кандидата** на пакете и данных с айфона.
2. **Цифры:**
   - свои пары: сколько совпало;
   - чужие пары: сколько ложно совпало, отдельно — Кимы;
   - непригодные кадры: какую причину дал;
   - плохие эталоны: отклонены ли;
   - антиспуфинг: живой человек / фото с экрана / распечатка;
   - подсчёт людей: один / двое в кадре;
   - время на кадр и на один проход на CPU; сколько кадров в секунду тянем.
3. **Выбери стек и порог по цифрам.** Начинай с CPU; GPU — только если на проход уходит больше ~1 с.
4. **Форма модуля** (рекомендация, подтверди): отдельный контейнер `face` с HTTP API во внутренней сети и без своего хранилища. Эмбеддинг эталона хранит бэкенд в PostgreSQL вместе с версией модели и передаёт его при сравнении. Черновик API — в `face/docs/api.md`.
5. **Запиши решения:** что выбрали, какие были варианты, почему, чем рискуем. Они пойдут в общий журнал решений.

## Этап 4. Реализация (≈ 80 мин)

- Сервис в `face/app/`: Python 3.12, FastAPI.
- Dockerfile в `face/`: модели встраиваются при сборке, сервис работает с `--read-only` и не от root.
- Приём видео с камеры выбранным на этапе 1 способом.
- Тестовая консоль в `face/tools/`: фото пакета, видео или фото с айфона → рамки, число людей, совпадение, «живость», причина. Это обязательная задача: по ней команда и судьи видят, что сервис работает.
- **Живой просмотр в вебе (требование человека):** открыть видео с камеры, на котором в реальном времени рисуются рамки вокруг людей и их число. Отдельная вкладка — видео с распознаванием лиц: рамки лиц, совпадение с эталоном, «живость», причина. Конвейер тот же, что для проходной.
- Тесты в `face/tests/`, финальный прогон оценки с отчётом в `face/docs/`.
- Сначала задачи «Обязательно», потом «Желательно».

Подготовь для человека, не трогая чужие файлы:
