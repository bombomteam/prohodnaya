# Антиспуфинг MiniFASNet (Silent-Face-Anti-Spoofing, minivision-ai)

Пассивная проверка «живое лицо или подмена» по одному RGB-кадру. Две маленькие сети (≈0,4 млн параметров каждая) на кропах 80×80 вокруг лица с разным масштабом контекста. Их ответы складываются. Веса из исходного репозитория экспортированы в ONNX и работают через onnxruntime на CPU. torch нужен только для экспорта.

## Воспроизведение

Из корня репозитория:

```bash
~/bin/uv venv --python 3.12 face/eval/bench/minifasnet/.venv
~/bin/uv pip install -p face/eval/bench/minifasnet/.venv/bin/python --index-strategy unsafe-best-match \
    -r face/eval/bench/minifasnet/requirements.txt
# .pth + экспорт в ONNX (export_onnx.py) с проверкой sha256:
MINIFASNET_EXPORT_PYTHON=face/eval/bench/minifasnet/.venv/bin/python face/models/fetch_models.sh minifasnet
# или отдельно экспорт и проверка на реальных кропах (нужны веса YuNet: fetch_models.sh opencv):
face/eval/bench/minifasnet/.venv/bin/python face/eval/bench/minifasnet/export_onnx.py \
    --image "case_prerekvizity/Case1_Package1/Первый пакет/Персонал/Ким Андрей Сергеевич/Ким_Андрей_Сергеевич_фото.jpg"
```

`--index-strategy unsafe-best-match` нужен uv, чтобы `torch==2.14.1+cpu` брался с индекса PyTorch CPU, а остальное — с PyPI. Обычный pip понимает `--extra-index-url` внутри `requirements.txt` сам. Установка в чистое окружение даёт тот же `pip freeze`, проверено.

## Контракт ONNX (оба файла)

| | Имя | Тип и форма | Смысл |
| --- | --- | --- | --- |
| вход | `input` | float32 `[N, 3, 80, 80]` | кроп **BGR**, значения **0..255** (без деления на 255, без mean/std) |
| выход | `prob` | float32 `[N, 3]` | softmax по 3 классам; **индекс 1 — живое лицо**, 0 и 2 — классы подмены |

Softmax встроен в граф, как в исходном `AntiSpoofPredict.predict`: `F.softmax(model(img))`.

## Точная предобработка из исходного репозитория

Пайплайн `test.py` → `src/anti_spoof_predict.py` + `src/generate_patches.py`. Повторять его в адаптере дословно.

1. **Изображение — BGR uint8,** как у `cv2.imread`. EXIF-поворот применять до этого. `test.py` дополнительно требует соотношение W:H = 3:4 (`check_image`) — «для совместимости с видеопотоком Android APK». Для сети это не обязательно, но это распределение, на котором её проверяли (портретные кадры фронтальной камеры телефона).
2. **Рамка лица.** Свой детектор `Detection.get_bbox`: RetinaFace (Caffe, `resources/detection_model/Widerface-RetinaFace.caffemodel` + `deploy.prototxt`).
   - Изображение уменьшается до площади около 192×192 с сохранением пропорций, `blobFromImage(img, 1, mean=(104,117,123))`.
   - Берётся **одна** рамка с максимальной уверенностью. Порог 0.6 объявлен (`detector_confidence`), но не применяется.
   - Рамка `[x, y, w, h]` в пикселях исходного кадра: `x = int(left)`, `y = int(top)`, `w = int(right - left + 1)`, `h = int(bottom - top + 1)`.
   - **В OpenCV 5.0 этот детектор не загрузить:** нет `cv2.dnn.readNetFromCaffe`. Используем рамку SCRFD или YuNet; как они отличаются — ниже.
3. **Параметры по имени файла** (`utility.parse_model_name`):
   - `2.7_80x80_MiniFASNetV2.pth`: масштаб **2.7**, вход 80×80, сеть `MiniFASNetV2`;
   - `4_0_0_80x80_MiniFASNetV1SE.pth`: масштаб `float("4")` = **4.0**, вход 80×80, сеть `MiniFASNetV1SE`;
   - ядро `conv_6_dw` = `get_kernel(80, 80)` = `((80+15)//16, (80+15)//16)` = **(5, 5)**.
4. **Кроп** (`CropImage._get_new_box` + `crop`) — для каждой модели со своим масштабом `s`:
   - `s = min((src_h-1)/h, (src_w-1)/w, s)` — масштаб **урезается**, если расширенная рамка не помещается в кадр;
   - `new_w = w*s`, `new_h = h*s`; центр `cx = x + w/2`, `cy = y + h/2`;
   - `x1 = cx - new_w/2`, `y1 = cy - new_h/2`, `x2 = cx + new_w/2`, `y2 = cy + new_h/2`;
   - если рамка вылезла за край, она **сдвигается** внутрь, а не обрезается. При `x1 < 0`: `x2 -= x1; x1 = 0`. При `x2 > src_w-1`: `x1 -= x2-src_w+1; x2 = src_w-1`. Так же по `y`;
   - координаты через `int()` (отбрасывание дробной части), вырез **включительно**: `img[y1 : y2+1, x1 : x2+1]`;
   - `cv2.resize(crop, (80, 80))` с интерполяцией по умолчанию (`INTER_LINEAR`). **Пропорции не сохраняются:** прямоугольный вырез сжимается в квадрат, так и задумано.
5. **Тензор** (`data_io/functional.to_tensor`): `HWC → CHW`, `float32`, **без `/255`** (в исходнике `return img.float()`, деление закомментировано), без нормализации, порядок каналов **BGR**. Ровно это ждёт вход `input` в ONNX.
6. **Выход одной модели:** softmax по 3 логитам.
7. **Объединение двух моделей** (`test.py`):
   - `prediction = prob_V2 + prob_V1SE` (форма 1×3);
   - `label = argmax(prediction)`;
   - `score = prediction[label] / 2`;
   - `label == 1` → «Real Face», иначе «Fake Face».

   Порога, кроме argmax, в исходнике нет. В APK порог задаётся на уверенность. В адаптере естественно брать `live = (prob_V2[1] + prob_V1SE[1]) / 2` и порог, подобранный по нашим данным.
8. **Классы 0 и 2.** Репозиторий не документирует, какая подмена какой класс (`datasets/README.md` показывает только папки `0/1/2`). Опираться можно только на «1 = живое».

## Рамка детектора: исходный RetinaFace против SCRFD и YuNet

Кроп строится от рамки, поэтому рамка другого детектора меняет вход сети. Замер на всех 78 изображениях пакета: исходный RetinaFace (Caffe, во временном окружении с `opencv-python-headless==4.14.0`, логика `get_bbox` дословно) против SCRFD `det_10g` и YuNet. Пары с IoU ≤ 0.5 исключены, у каждого детектора таких 3 из 78. У YuNet это 2 «пропуска», где RetinaFace выдал вырожденную рамку шириной в несколько пикселей, и 1 кадр проходной с IoU 0.50. Остаётся по 75 пар. Отношения медианные:

| Детектор | IoU | ширина / ширина RetinaFace | высота / высота RetinaFace | сдвиг центра по y, в долях высоты RetinaFace |
| --- | ---: | ---: | ---: | ---: |
| SCRFD (insightface) | 0.73 | 0.85 | 1.15 | −0.07 (выше) |
| YuNet (OpenCV) | 0.72 | 0.86 | 1.21 | −0.06 (выше) |

Рамки SCRFD и YuNet уже и выше исходной. Средняя вероятность «живое» (сумма двух моделей / 2) и число кадров с `live > 0.5`:

| Группа (n) | Рамка RetinaFace | Рамка SCRFD | Рамка YuNet |
| --- | --- | --- | --- |
| эталоны `фото` (10) | 0.950, 10/10 | 0.996, 10/10 | 0.994, 10/10 |
| фото пропуска на столе (8) | 0.091, 0/8 | 0.136, 0/8 | 0.169, 0/8 |
| кадры проходной (57) | 0.930, 57/57 | 0.920, 57/57 | 0.874, 52/57 |

С рамкой SCRFD результат близок к исходному. С YuNet на 5 кадрах проходной вероятность «живое» падает ниже 0.5. Если детектор — YuNet, рамку можно привести к виду RetinaFace по медианам выше:

- `w_r = w/0.86`, `h_r = h/1.21`;
- центр: `cx_r = cx`, `cy_r = cy + 0.06*h_r`.

Для SCRFD то же с 0.85, 1.15 и 0.07. Так не проверялось, это гипотеза для прогона.

**Чего эти числа НЕ показывают.** Изображения пакета квадратные 1024×1024. «Пропуск» — фото бумажного пропуска на столе, а не лицо с экрана или распечатка перед камерой. Настоящих атак «телефон с фото перед камерой» и «распечатка» здесь нет. Их надо снять на айфон (этап 1 плана) и только по ним выбирать порог и делать выводы о защите.

## Подводные камни

1. **OpenCV 5.0 без Caffe:** исходный детектор не загрузить, нужна рамка SCRFD или YuNet (см. выше). Если понадобится исходный детектор, нужен `opencv-python-headless<5` (проверено на 4.14.0). Его веса (`Widerface-RetinaFace.caffemodel`, 1 866 013 Б) лежат в том же репозитории, но в `face/models/` не скачиваются.
2. **Урезание масштаба.** При крупном лице в кадре `s` урезается до `(src_h-1)/h`. Пример: кадр 1280×720, лицо высотой 300 px. Для V1SE масштаб 4.0 → 2.4, а для V2 2.7 → 2.4: обе модели получают почти одинаковый контекст, меньше, чем при обучении. При лице во весь кадр контекста нет совсем. Держать лицо не слишком крупным: это требование к съёмке.
3. **Вне распределения обучения.** Состав обучающих данных в репозитории не описан. По `test.py` (кадры 3:4 «как в видеопотоке Android APK») и README модели рассчитаны на кадры камеры телефона в сценарии их APK. Задняя камера iPhone 16 Pro с 0,6–1 м и альбомный кадр 1280×720 — скорее всего, другое распределение. Порог подбирать только по своим съёмкам. README репозитория прямо пишет: «Because the robustness of RGB silent living detection depending on camera model and scene, the actual use experience could be different» и «the rotation angle and vertical direction of the face are less than 30 degrees».
4. **torch 2.14: экспорт по умолчанию — dynamo,** и ему нужен `onnxscript`. В `export_onnx.py` стоит `dynamo=False` (legacy TorchScript-экспортёр, печатает `DeprecationWarning`). Если в будущих версиях torch его уберут, поставить `onnxscript`, экспортировать с `dynamo=True` и заново проверить расхождение torch и ort.
5. **`torch.load(..., weights_only=True)` работает:** в `.pth` лежит только `state_dict` из тензоров. Префикс `module.` (DataParallel) снимается так же, как в исходнике, хотя в этих двух файлах его нет.
6. **Ошибки в порядке каналов и диапазоне незаметны,** сеть всё равно что-то выдаст. Обязательны BGR и 0..255. RGB или `/255` дадут правдоподобные, но неверные вероятности.
7. **Чего не ловит** (не заявлять обратного): качественное видео или фото на экране с близкого расстояния, маски, 3D. Пассивная проверка по одному кадру — дешёвый барьер, не гарантия.
8. **Альтернатива:** в `insightface` 2.1 есть своё RGB-дополнение `liveness` (вход 80×80, см. `../insightface/SETUP.md`). Его веса под некоммерческими условиями insightface, и оно не проверялось.
