# Роли, права и интерфейсы

Статус: спецификация MVP для разработки React и FastAPI. Четыре бизнес-роли взяты из раздела 2 [кейса](../case_prerekvizity/Кейс_1_Проходная_v2_КОТИК_на_ТРОНЕ.md). Детальная матрица, маршруты и разделение полномочий ниже — решения проекта, а не дословные требования кейса. Вход и роли реализуются через [Keycloak](authentication.md).

## 1. Какие роли нужны

| Роль Keycloak | Пользователь | Основная задача | Устройство и стартовый экран |
| --- | --- | --- | --- |
| Ключ устройства, без роли Keycloak | Рабочий | Предъявлять подтверждение и передавать координаты во время своей смены | Телефон, `/worker` |
| `controller` | Контролёр на проходной | Начать вход/выход, снять лицо, увидеть серверное решение | Планшет/компьютер с камерой, `/checkpoint` |
| `admin` | Администратор приложения | Управлять людьми, привязками и планом, разбирать журнал | Компьютер, `/admin/people` |
| `manager` | Руководитель объекта | Смотреть присутствующих, аналитику, отчёты и помощника | Компьютер, `/management/overview` |

Один React-проект может содержать все четыре раздела. Рабочий — бизнес-пользователь, но не роль Keycloak: его права определяются подписью зарегистрированного ECDSA-ключа. Совмещение операторских ролей не даёт права подписывать за рабочего. Административные и управленческие экраны можно объединить общей оболочкой. Роли могут совмещаться; доступные действия объединяются, но роль администратора не даёт автоматического права проводить человека через проходную — для этого назначается `controller`.

Отдельно существуют технический администратор Keycloak и служебная учётная запись backend для ограниченных операций управления аккаунтами. Это не пользовательские роли продукта; им не требуется отдельный React-интерфейс. Обычный `admin` не получает управление realm, OIDC-клиентами или инфраструктурными секретами.

## 2. Матрица прав

`—` означает запрет. Все разрешения проверяются FastAPI, включая принадлежность данных. В MVP права относятся к единственной настроенной площадке; при появлении нескольких объектов потребуется серверная проверка назначения пользователя на объект.

| Действие | Рабочий: ключ | controller | admin | manager |
| --- | --- | --- | --- | --- |
| Войти/выйти через Keycloak | Не применяется | Да | Да | Да |
| Видеть свою рабочую карточку и состояние смены | Только своё | — | Через карточку человека | — |
| Выполнить первоначальную привязку телефона | Только свою после разрешённого выпуска | — | Инициировать/отозвать/перевыпустить привязку рабочего | — |
| Предъявить доказательство прохода | Только своё | — | — | — |
| Отправлять координаты | Только в свою открытую смену | — | — | — |
| Инициировать вход/выход, отправить кадр | — | Да | — | — |
| Смотреть результат попытки | Своей | Обслуживаемой им | Через журнал | Через журнал только чтение |
| Создать/редактировать/деактивировать рабочего | — | — | Да | — |
| Загрузить/заменить эталон лица | — | — | Да, с серверной проверкой | — |
| Выпустить/отозвать enroll-код рабочего | — | — | Через backend | — |
| Назначать повышенные роли | — | — | — | — |
| Смотреть реестр людей и административную карточку | — | — | Да | Только сведения в отчётах |
| Смотреть журнал проходов | — | Только текущую обслуживаемую попытку | Да | Да, только чтение |
| Смотреть присутствующих | — | — | Да | Да |
| Настраивать план, зоны и привязку координат | — | — | Да | Только чтение |
| Смотреть маршруты, аналитику, отчёты | — | — | Да | Да |
| Задавать вопросы и получать сводки | — | — | Да | Да |
| Принудительно разрешить проход/править время смены | — | — | — | — |

Назначение `controller`, `admin`, `manager` выполняет технический администратор IAM по установленной процедуре; UI создания рабочего выпускает enroll-код, не создаёт аккаунт IAM и не назначает роли. Если позже понадобится делегирование ролей через продукт, оно оформляется отдельным решением с аудитом и ограничением повышения привилегий.

Успешная серверная проверка автоматически меняет смену. Ни одна роль не имеет кнопки обхода проверки лица/телефона. Исторические попытки и координаты не редактируются и не удаляются через обычный UI. Деактивация человека не стирает историю.

## 3. Общие экраны и навигация

- `/login` операторов: переход в Keycloak. Собственный парольный вход допускается только в явно объявленном fallback из authentication.md. Рабочий открывает интерфейс регистрации/ключа без IAM.
- После входа оператора backend возвращает проверенный профиль и роли; рабочий получает свою карточку через доказательство владения ключом. React показывает разрешённые разделы.
- Одна роль ведёт на её стартовый экран; несколько ролей — на выбор доступного раздела. Переключение раздела не меняет роль и не расширяет права.
- Оператор без назначенной роли видит «Доступ не назначен», без данных приложения.
- На прямой переход к запрещённому маршруту React показывает отказ; прямой запрос API независимо отклоняет backend. Невалидный токен — 401, недостаточное право — 403; единый 404 для сокрытия чужого ресурса можно добавить после хакатона; для MVP достаточно согласованного отказа без выдачи данных.
- В общей оболочке: имя, доступные разделы, выход, понятное состояние ошибки соединения. Выход из аккаунта не закрывает физическую смену.

## 4. Рабочий: мобильный интерфейс

| Экран | Что показывает | Действия |
| --- | --- | --- |
| `/worker` — моя смена | Имя, готовность телефона, внутри/вне объекта, начало открытой смены, состояние отправки координат | Перейти к подтверждению, открыть настройку телефона |
| `/worker/setup` — привязка | Ожидает привязки / готово / отозвано, понятная инструкция | Завершить разрешённую привязку; запросить разрешение геолокации |
| `/worker/pass` — проход | Текущая попытка и направление, срок ожидания, результат сервера | Связать телефон с попыткой выбранным протоколом и предъявить своё доказательство |

Первичная настройка: одноразовый enroll-код/QR → создание неизвлекаемого ECDSA-ключа → регистрация `/enroll`. Проход: подпись nonce конкретной сессии. Форматы сверяются с 01–08. На телефоне нет выбора чужого человека и кнопки самостоятельного открытия смены. После разрешённого входа состояние и сбор координат обновляются по серверу; после выхода сбор останавливается. При устаревшей связи UI не показывает локальное предположение как успешный проход.

Необходимы крупные элементы для работы на телефоне, состояния отсутствия разрешений и повторного входа. Просмотр полной личной истории смен можно добавить позже; он не заменяет обязательные функции.

## 5. Контролёр: интерфейс проходной

Основной экран `/checkpoint` объединяет весь обязательный сценарий:

1. Выбор направления «Вход»/«Выход» и начало новой попытки.
2. Отображение идентификатора/способа связи попытки с телефоном согласно протоколу.
3. Камера, предпросмотр кадра и действие захвата; состояние отсутствия камеры или разрешения.
4. Отдельные состояния «ждём телефон», «ждём кадр», «проверяем».
5. Крупный результат «Разрешено» либо «Отказ»/«Ошибка» с человеческой причиной.
6. Переход к следующей попытке; повтор после ошибки создаёт новую попытку по правилам сервера.

Показывать только необходимые сведения обслуживаемой попытки: установленное имя, направление, время и результат. Не предоставлять контролёру массовую биометрию, маршруты или редактирование рабочего. Ожидание, повторный запрос или смена направления не должны переиспользовать разрешение прежней попытки.

## 6. Администратор: управление объектом

| Экран | Содержание | Действия |
| --- | --- | --- |
| `/admin/people` | Реестр, поиск, состояние человека и наличие открытой смены | Создать человека, открыть карточку |
| `/admin/people/new` | Данные человека, загрузка эталона, результат пригодности | Сохранить после проверки; исправить отклонённый материал |
| `/admin/people/:id` | Данные, состояние, привязка ключа телефона, эталон с ограниченным доступом, сведения о смене | Редактировать, заменить эталон, деактивировать, выпустить enroll-код, отозвать/перевыпустить средство подтверждения |
| `/admin/site` | План по материалам кейса, зоны, настройка привязки координат | Загрузить план, настроить и сохранить зоны/преобразование через UI |
| `/admin/access-log` | Попытки: время, человек или «не установлен», направление, результат, причина | Фильтровать и просматривать детали; без правки истории |

Поиск и фильтры реестра/журнала — предложения для удобства. Серверная проверка материала, правка людей, журнал и настройка координат через UI обязательны по кейсу. Выпуск enroll-кода и регистрация ключа показывают актуальный статус; повтор использованного кода отклоняется. Рабочему не требуется логин/пароль.

Деактивация при открытой смене требует заранее описанного правила: нельзя незаметно закрывать её или оставлять человека без предусмотренного процесса выхода. Принятое правило: такой случай показывается администратору и операция отклоняется; история сохраняется.

## 7. Руководитель: обстановка и аналитика

| Экран | Содержание и действия |
| --- | --- |
| `/management/overview` | Количество и список людей внутри, время входа, доступное последнее положение с давностью; обновление данных |
| `/management/movements` | План, посещаемость зон и маршруты; легенда людей, название метрики, визуальное отличие нулевой активности; общие фильтры дня/диапазона/часов/одного, нескольких или всех людей |
| `/management/reports` | Отчёт по конкретной смене и по человеку за период, фактическое время и статус незавершённой смены |
| `/management/access-log` | Журнал с причинами отказов, только чтение; можно переиспользовать компонент административного журнала |
| `/management/assistant` | Вопрос обычным языком и сводка за период, ответ по данным системы, период, нет данных, ошибка и повтор |

Администратор имеет доступ к этим экранам по матрице. Показ в реальном времени без обновления страницы и экспорт в файл — бонусы, а не условия готовности базового интерфейса. Карта не скрывает человека из присутствующих при потере геолокации.

## 8. Критерии готовности

1. Каждая роль проходит свой сценарий в React без Swagger, консоли Keycloak или ручных HTTP-запросов; инфраструктурная настройка IAM выполняется по отдельной инструкции.
2. Для каждой операции матрицы проверены разрешённая роль, запрещённая роль и, где применимо, чужой ресурс. Проверяется прямой запрос API, а не только наличие кнопки.
3. Многоролевой пользователь видит объединение разрешений; отсутствие роли не предоставляет доступ по умолчанию.
4. Все экраны работают на реальных серверных данных, показывают загрузку, пустое состояние и ошибку. В проходе ожидание/ошибка не выглядят как разрешение.
5. Рабочий проверен на телефоне, проходная — на устройстве с камерой, администратор и руководитель — на компьютере.
6. У нового человека работают регистрация, привязка, вход, координаты, выход, журнал и отчёт; чужое лицо и повторное доказательство отклоняются.

Это спецификация целевого поведения. Ни UI, ни проверка прав пока не считаются реализованными по наличию этого файла.
