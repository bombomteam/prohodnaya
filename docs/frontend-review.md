# Проверка фронтенда по кейсу и ролям

Проверен коммит `8bb925a`, полученный из `origin/main`. Основания: [кейс](../case_prerekvizity/Кейс_1_Проходная_v2_КОТИК_на_ТРОНЕ.md), [роли и интерфейсы](roles-and-interfaces.md), [аутентификация](authentication.md), [пайплайн](system-workflow.md).

Вывод: есть содержательный браузерный прототип всех четырёх направлений работы, но это ещё не ролевой фронтенд готового решения. Keycloak отсутствует, права не влияют на навигацию и загрузку, данные и проходы по умолчанию имитируются. Переключение `mode: api` само по себе не закрывает эти пробелы.

## Что проверено

- Выполнен `git pull --ff-only`, обновление `47ef027 → 8bb925a`, без конфликтов.
- Прочитаны отображение, обработчики, транспорт, демоадаптер, WebAuthn, контракт API, Dockerfile и entrypoint, ограничения и тест.
- `npm test` — прошёл 1 тест демоадаптера: регистрация, привязка, вход/выход, точка, маршрут и отчёт, повтор использованного подтверждения и точка после закрытия.
- `npm run build:pages` — успешно создан статический сайт.

## Основные проблемы по приоритету

### P0 — нет входа через Keycloak и ролевого UI

`frontend/src/app.js:16–26, 68–82, 163–168`: все разделы видны всем, переход не проверяет роли, начальная страница всегда общая «Обстановка». Нет входа, logout, получения проверенного профиля и обработки пользователя без роли. Поле `employee.role` обозначает специальность рабочего и не является ролью Keycloak.

`frontend/src/api.js:11–21`: запросы отправляют cookie через `credentials: include`, без access token. Документ `frontend/docs/frontend-api.md` также описывает cookie-сессию и противоречит выбранному в корневой документации Bearer/OIDC-контракту. Backend-for-frontend с cookie может быть отдельным решением, но сейчас он не реализован и не описан как интеграция Keycloak.

Исправление: интегрировать OIDC, профиль и роли, серверные guards, ролевую навигацию, обновление токена и 401/403. UI-ограничения не заменяют проверки FastAPI.

### P0 — загрузка экранов несовместима с матрицей прав

`frontend/src/app.js:47–65`: экран рабочего и проходная сначала вызывают `api.dashboard()`. По нашей матрице общий список присутствующих и журнал не доступны `worker` и `controller`. При корректном 403 общий `catch` прерывает загрузку; рабочий даже не дойдёт до `api.me()`.

Там же аналитика вызывает `api.employees()` — административный реестр, недоступный руководителю. Его отказ прервёт получение плана, аналитики и отчёта. Сама аналитика показывает форму изменения плана всем (`app.js:138`), хотя руководителю разрешено только чтение.

Исправление: убрать общие запросы из рабочего/проходной; руководителю дать отдельный разрешённый справочник для фильтра; разделить чтение аналитики и административную настройку плана.

### P0 — реальные гарантии кейса отсутствуют

`frontend/config.js:4`, `frontend/src/demo-api.js:10–54`: по умолчанию браузерные примеры и localStorage. Решение о демопроходе принимается локально, нет реальной проверки лица и БД. Это честно обозначено баннером, поэтому допустимо как прототип, но не как предъявляемое выполнение кейса.

В полученном репозитории нет реализации FastAPI/PostgreSQL/Keycloak и общесистемного Compose. Есть интерфейс HTTP и фронтенд-контейнер; они не доказывают серверную проверку, сохранность или взаимодействие разных устройств. Помощник в демо возвращает `unavailable`, провайдеры модели отсутствуют.

Исправление: интегрировать реальные сервисы и пройти сценарий на новом человеке через отдельные устройства. Это зависимость от backend, а не требование перенести его работу во frontend.

### P1 — администрирование не покрывает принятую спецификацию

`frontend/src/app.js:105–110`, `frontend/src/api.js:37–39`: есть создание/редактирование полей и загрузка фото. Нет административной карточки с привязкой аккаунта Keycloak, состояния частичной регистрации, деактивации, отзыва и перевыпуска телефонного средства. Есть только самостоятельная привязка рабочего.

Исправление: добавить жизненный цикл человека и привязок по `roles-and-interfaces.md`. Валидация эталона остаётся серверной. Нельзя утверждать, что она работает, по пояснению рядом с загрузкой файла.

### P1 — план условный, загрузка реальной схемы отсутствует

`frontend/src/app.js:131–139`, `frontend/src/api.js:57–58`: UI показывает сетку 3×3 и позволяет менять границы и девять названий. Сетка как способ разбиения допустима; проблема — отсутствие ввода/отображения план-схемы по предоставленным изображениям, что требует раздел 5.3 кейса. Ограничение уже признано в `frontend/docs/limitations.md`.

Исправление: подготовить план по материалам, обеспечить его ввод и отображение, согласовать координатную привязку; административную запись отделить от просмотра руководителем.

### P1 — регулярный render уничтожает незавершённые действия

`frontend/src/app.js:149–151, 161, 224–235, 288–307`: `render()` полностью заменяет DOM. На телефоне очередная точка геолокации вызывает render и сбрасывает введённый код подтверждения. На проходной изменение статуса challenge может удалить активный video во время захвата; у `run()` нет общей защиты от повторного вызова действий, чьи кнопки не disabled.

Исправление: обновлять части экрана без уничтожения формы/камеры либо сохранять ввод в состоянии. Проверить активную геолокацию во время ввода кода выхода, получение кадра и обновление challenge одновременно, повторные нажатия. Это дефект UI, не доказательство обхода серверной защиты.

### P1 — отмена нового сотрудника оставляет поля в форме

`frontend/src/app.js:174–180`: при открытии диалога перезаписываются только id/name/company/role. `referencePhoto` и подпись файла не сбрасываются. После выбора фото человека A, отмены и открытия формы человека B может быть отправлено прежнее фото A; проверка «на фото одно лицо» этого не обнаружит.

Исправление: сбрасывать форму и загрузку при открытии для другого человека/новой записи, показывать явно выбранное фото, отдельно обозначать сохранённый эталон и его замену.

### P2 — несоответствия аналитики, статусов и восстановления

- `app.js:135–138`: легенда маршрутов есть, но только пять цветов, затем они повторяются; более пяти людей нельзя однозначно различить на схеме по одному цвету. Добавить различимые стили/выделение выбранного маршрута.
- `app.js:29–30` форматирует время в часовом поясе браузера, а календарные фильтры используют Москву (`app.js:6`). На другом устройстве подписи могут расходиться с периодом. Использовать часовой пояс объекта единообразно.
- `demo-api.js:160–172`: отчёт отбирает смены по дате начала и считает всю длительность, не учитывает часы фильтра/пересечение периода. Это ограничение демо; реальный сервер должен реализовать согласованное правило.
- `app.js:39, 118, 145–146`, контракт API: результат бинарный allowed/denied; pending/error не выделены. При сетевом сбое решение может уже быть принято сервером, но UI не имеет явного восстановления конечной попытки и идемпотентного ключа действия.
- `app.js:288–290`: ошибки опроса проходной скрываются; ожидание может выглядеть исправным при потере связи. Показывать состояние связи и возможность получить окончательный результат.
- `api.js:11–21`: signal поддержан транспортом, но вызовы не задают таймаут. Зависший запрос может держать `busy` и блокировать действия без управляемого завершения.
- `app.js:218–235`: геолокация включается вручную и может быть выключена в открытой смене. Нужно явно показывать отсутствие отслеживания и определить сценарий обязательного сбора; браузерный фон не проверен.

### P2 — выбранный React пока не используется

`frontend/package.json`, `frontend/index.html`, `frontend/src/app.js`: приложение написано на JavaScript с шаблонными строками и `innerHTML`, зависимостей React нет. Сам кейс React не требует, но это расхождение со стеком команды. Либо перейти на React, либо явно пересогласовать стек; не называть текущий код React-приложением.

## Покрытие интерфейсов

| Роль | Уже есть в прототипе | Не хватает для спецификации |
| --- | --- | --- |
| Рабочий | Своя смена в API-контракте, WebAuthn-вызовы, ввод кода, геолокация | Вход и ролевой раздел, реальная безопасная привязка, восстановление ошибок/отзыва, загрузка без запрещённого dashboard |
| Контролёр | Направление, challenge, камера, отправка кадра, причина результата | Авторизация, разграничение попыток, отказ от общего dashboard, статус ошибки/ожидания и восстановление решения |
| Администратор | Реестр, создание, редактирование, фото, журнал, границы/названия зон | Карточка и жизненный цикл, аккаунт Keycloak, отзыв/перевыпуск, реальный план и права записи |
| Руководитель | Присутствующие, время входа, фильтры, карта, маршруты с легендой, сводные смены, формы помощника | Ролевой доступ, read-only настройка, допустимый справочник людей, давность положения, реальная модель и серверные данные |

Отчёт по сменам и людям отображается в аналитике, отдельный URL не обязателен для кейса. В таблице смен есть начало, конец и минуты, но нет отдельного детального просмотра выбранной смены с её маршрутом; если он нужен как целевой отчёт, добавить выбор конкретной смены. Предложенные в документации URL — решение команды, не основание само по себе считать экран отсутствующим.

## Рекомендуемый порядок исправлений

1. Согласовать единый OIDC/API-контракт и реализовать Keycloak, роли, профиль и допустимые загрузки экранов.
2. Завершить серверный вертикальный сценарий нового рабочего: регистрация, привязка, вход/выход, отказ, журнал и постоянное хранение.
3. Исправить потерю ввода/камеры при render и сохранение чужого файла в диалоге; добавить восстановление статуса попытки.
4. Дополнить администрирование и настоящий план; подключить координаты, общий часовой пояс и отчёты.
5. Подключить модель и локальный провайдер, затем выполнить живую ролевую приёмку на разных устройствах, перезапуск и проверки обхода.

Код продукта в рамках проверки не изменялся. Этот отчёт фиксирует найденные пробелы, а не заменяет исправление или живой прогон.
