# Сценарий для жюри

Откройте https://hack-detect.duckdns.org и выберите роль. Пароль не нужен: на стартовой странице четыре карточки: **Администратор**, **Контролёр**, **Руководитель**, **Телефон рабочего**. Клик по роли сразу открывает её экран (демо-вход, токен выдаёт Keycloak). Роль можно сменить без выхода переключателем над каждым экраном; под ним строка «Что здесь проверить». Те же семь шагов с кнопками-переходами есть в приложении: кнопка «Как проверить кейс» на старте и пункт меню внутри. Около десяти минут. Обычный вход через Keycloak остаётся: ссылка «Войти через Keycloak» на старте.

Состояние на 10.10.2026, `main` на `621fa84`. Шаги составлены по экранам фронта (`frontend/src/landing.js`). Проход разрешённым лицом проверяется только живым человеком перед камерой: на автоматических прогонах это не подтверждалось ([limitations.md](limitations.md)).

## Что понадобится

- Браузер с камерой (разрешите доступ, когда спросит) и HTTPS-адрес стенда: камера и ключ телефона работают только по HTTPS.
- Для шагов 1–3: живой человек и его фото лица (один человек в кадре, лицо видно целиком). Это может быть член жюри со своим фото. Фото не попадает в репозиторий.
- Для шага 4: второй человек, чужой для первого.
- Телефон рабочего открывается в соседней вкладке (ссылка `?worker=1`) или на настоящем телефоне; вёрстка мобильная: вкладки внизу, экран телефона рабочего во весь экран.

| 2 | **Телефон рабочего**: откройте ссылку из шага 1 или впишите код в поле «Код для телефона», «Привязать устройство» | Надпись «Устройство привязано». Если пишет, что телефон не привязан, вернитесь к шагу 2 |
| 4 | **Контролёр**, «Проходная»: то же, но перед камерой другой человек | «Отказ в проходе: лицо не совпадает»; смена не открыта; отказ записан в журнал | Если чужой прошёл, не выдавайте это за норму: запишите время и сообщите организаторам. В «Аналитике» маршруты и посещаемость трёх зон за день; «Табель сотрудника» → «Получить отчёт» даёт отчёт по человеку | Пусто: данных за выбранный день нет, сначала выполните шаги 1–3. Маршруты строятся по точкам, которые присылают телефоны рабочих |
| 6 | **Руководитель**, «Помощник» | Ответ на вопрос обычным языком. Проверьте пять вопросов из п. 4.2 кейса: «Кто сейчас на объекте?», «Сводка за сегодня», «Кто вчера отработал меньше четырёх часов?», «В какой зоне вчера было больше всего людей?», «Были ли отказы на входе за неделю и почему?». ## Если что-то пошло не так

- Любая ошибка при проверке лица, в том числе недоступность модуля или ответ дольше 10 секунд, даёт **отказ**, а не пропуск, и запись в журнал. Это правильное поведение.
- Вход по кнопке роли не сработал: попробуйте «Войти через Keycloak» (логины `admin1`, `manager1`, `controller1`, пароли у организаторов, в Git их нет).
- Телефон не открывает ссылку: используйте вкладку `?worker=1` на компьютере.
- Стенд один на всех, любой push в `main` выкатывается на него сразу. Во время показа в `main` не пушить ([pipeline.md](pipeline.md)); автооткат возвращает прошлый релиз, ручной откат: Actions, Rollback.

## Для организаторов (до показа)

- Стенд жив: адрес открывается, на сервере `healthcheck.sh` ([run.md](run.md)); консоль модуля лиц показывает `models_loaded: true`.
- Демо-вход без пароля включён флагом `DEMO_LOGIN=true` только на стенде; в проде его выключают ([limitations.md](limitations.md)).
- Перезапуск для шага 7 делает DevOps через `deploy/dc restart backend db`; никогда не `down -v`.

## Какие пункты кейса что закрывает

Решение о проходе на сервере и чужой не проходит: шаги 3 и 4. Данные переживают перезапуск: шаг 7. Помощник и смена провайдера настройкой: шаг 6. Человек, которого назовут судьи: повторить шаги 1–3 для него.
