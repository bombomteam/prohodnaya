# Аутентификация и права доступа

Статус: согласованная целевая схема, не подтверждение реализации. Источники: исходный кейс и решения команды, переданные пользователем. Файлы 00–08, включая `05-keycloak.md`, в текущем checkout отсутствуют; их детали не реконструируются. При появлении этих файлов сверить контракты с ними. См. [роли](roles-and-interfaces.md), [пайплайн](system-workflow.md) и [самопроверку](acceptance-checklist.md).

## Два способа идентификации

| Кто | Как устанавливается личность | Что проверяет backend |
| --- | --- | --- |
| Администратор, руководитель, контролёр | Keycloak, realm-роли `admin`, `manager`, `controller` | Access token: подпись, срок, issuer, audience; затем роль и доступ к ресурсу |
| Рабочий | Одноразовый enroll-код и зарегистрированный открытый ключ устройства | Подпись запроса, принадлежность ключа человеку, актуальность и одноразовость доказательства |

Рабочего нет в Keycloak: ему не создают пароль, роль `worker` или аккаунт через Admin API. Администратор создаёт доменную запись человека и выпускает enroll-код. Идентификаторы оператора `(issuer, sub)` сохраняются для аудита; рабочий определяется по проверенному ключу устройства. Приложение хранит людей, эталоны, ключи, смены, координаты и журнал в PostgreSQL.

## Вход операторов через Keycloak

1. React направляет оператора в Keycloak: Authorization Code + PKCE S256, публичный клиент `panel`, без client secret.
2. После обмена кода клиент получает токены. В API передаётся access token, не ID token. Токены находятся в памяти, не в localStorage, URL или логах.
3. FastAPI `current_user` проверяет подпись по JWKS, `exp`, `iss`, `aud` и допустимый алгоритм; возвращает `sub`, `preferred_username`, роли из `realm_access.roles`.
4. `require_role(...)` проверяет роль; принадлежность конкретного ресурса проверяет соответствующий сервис. Роли из тела запроса не доверенные.
5. 401: «Сессия истекла, войдите заново». 403: «Недостаточно прав». При невозможности обязательной проверки доступ не выдаётся.

Access token живёт около пяти минут. Это ограничивает, но не устраняет окно после logout/изменения ролей. Если нужен немедленный отзыв, потребуется отдельная серверная проверка. Logout оператора не закрывает смену рабочего.

## Конфигурация Keycloak и Compose

- Сервис `keycloak`: закреплённый образ 26.x, `start-dev --import-realm`, каталог `./keycloak/import` монтируется в `/opt/keycloak/data/import`.
- Realm `construction`; роли только `admin`, `manager`, `controller`.
- Public client `panel`: Standard Flow, PKCE S256, явные Redirect URIs и Web Origins для localhost и HTTPS-стенда.
- Клиент `access-api` используется как audience. В `panel` настраивается Audience mapper, включающий `access-api` в access token.
- `KC_INTERNAL_URL=http://keycloak:8080`: базовый внутренний адрес получения JWKS для realm `construction`. `KC_PUBLIC_URL`: публичный базовый адрес Keycloak; ожидаемый issuer — этот адрес плюс `/realms/construction`.
- Публичный hostname задаётся `KC_HOSTNAME`. За доверенным reverse proxy по согласованной схеме: `KC_PROXY_HEADERS=xforwarded`, `KC_HTTP_ENABLED=true`. Proxy должен контролировать forwarded-заголовки.
- Ключи кешируются с обработкой ротации; каждый API-запрос не требует обращения к Keycloak. Не принимать произвольный URL ключей из непроверенного токена.
- Пароль bootstrap-администратора и тестовых пользователей — только runtime-конфигурация. В `.env.example` описания и пустые значения секретов.

Основные контейнеры: frontend, backend, PostgreSQL, Keycloak. Для постоянного хранения Keycloak предпочтительна отдельная база/роль в том же PostgreSQL; встроенная БД start-dev допустима как явно описанный вариант стенда с persistent volume. Миграции приложения не меняют схему Keycloak.

Подготовить `admin1`, `manager1`, `controller1`. Безопасный экспорт realm и тестовых учёток не содержит паролей, хешей паролей или секретов. Если импорт не создаёт credentials, отдельная идемпотентная bootstrap-команда задаёт их из `.env`. В инструкции входа указать логины и способ получить пароли из локальной конфигурации; действующие пароли не коммитить даже в документации. Проверить импорт на пустом отдельном хранилище: пересоздание контейнера со старым volume не доказывает работу импорта.

## Регистрация телефона рабочего

1. Администратор через UI создаёт человека; backend проверяет эталон лица до принятия.
2. Backend выпускает одноразовый enroll-код, связанный с человеком и ограниченный сроком. Администратор передаёт его рабочему, например QR.
3. Телефон создаёт неизвлекаемый закрытый ключ ECDSA средствами WebCrypto; открытый ключ отправляется через `/enroll` с кодом и требуемым протоколом доказательством владения.
4. Backend атомарно потребляет код и сохраняет открытый ключ человека. Повторное использование и подмена владельца отклоняются. Закрытый ключ не передаётся серверу; механизм сохранения CryptoKey на устройстве сверяется с файлами 01/06.
5. Для прохода телефон подписывает свежий nonce конкретной сессии; backend проверяет подпись, срок, принадлежность попытке/направлению, отсутствие потребления, а также лицо с камеры. Только тогда меняется смена.
6. Координаты отправляются подписанными пачками в `POST /locations`. Backend устанавливает рабочего по ключу, проверяет подпись, защиту от повтора и свою открытую смену; `person_id` в теле не является доказательством.

Точная кривая ECDSA, формат подписи, канонизация данных, состав подписываемого сообщения, TTL, storage ключа и маршруты прохода должны быть взяты из файлов 01–08, когда они доступны. Не заменять этот протокол WebAuthn или логином рабочего по собственной инициативе. Неизвлекаемость ключа сама по себе не доказывает защиту от всех атак: нужны проверка nonce/контекста и сравнение лица.

## Запасной вариант и HTTPS

Если к отметке 1:30 от начала работы Keycloak не заработал, команда явно объявляет переход на собственный `/login` и JWT для трёх операторских ролей. Рабочий остаётся на ключе устройства. Fallback не называется выполнением требования Keycloak; его допустимость для сдачи нужно подтвердить у организаторов. Пароли хешируются на сервере, секрет подписи задаётся окружением, проверка токена и интерфейс `current_user`/`require_role` сохраняются. Не оставлять два скрыто взаимозаменяемых способа входа.

Для телефона и планшета нужен HTTPS: tunnel `cloudflared` либо reverse proxy перед приложением и Keycloak. Keycloak также доступен по HTTPS, иначе оператор не сможет пройти корректный браузерный вход. При quick tunnel адрес меняется: обновляются hostname, публичный URL, redirect URI и origins. Зафиксировать действия в инструкции запуска.

Точки синхронизации — относительные от старта: 1:30 конфиг фронтам и решение о fallback; 3:30 `auth.py`; 5:00 сквозной проход; 7:00 заморозка функций. Это ориентиры команды, не календарные дедлайны.

## Симулятор и сдача

Сиды: 5–10 вымышленных людей, 2–3 группы, план и 3–4 зоны. Эталонные фото команды — с согласия и вне Git. Симулятор использует виртуальные ECDSA-ключи, `/enroll` и подписанные пачки `/locations`, без записи напрямую в БД. Точки примерно раз в 30 секунд, допускается ускорение; `location_points.source` различает `phone` и `sim`. Открытие смен симулятора согласовать с backend и явно показать судьям; не выдавать тестовый обход за доказательство физического прохода.

Инструкция запуска и схема решения — отдельные файлы; текущие проектные документы не заменяют проверенную инструкцию. Пройти запуск на чистом клоне и [чек-лист приёмки](acceptance-checklist.md).
