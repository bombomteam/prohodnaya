# Переход на локальную модель

Для помощника руководителя. Провайдер выбирается настройкой, код менять не нужно. Состояние на 10.10.2026: слой `backend/app/llm/` и оба провайдера в `main`, по умолчанию `LLM_PROVIDER=ollama`. Сервис `ollama` описан в `compose.yaml` (профиль `backend`, видеокарта на стенде подключена в `deploy/compose.stand.yaml`), переменные есть в `.env.example`. **Не проверено:** запуск `ollama` в этом репозитории ещё не прогонялся (проверен только `docker compose config`). Первый выкат на стенд покажет, скачалась ли модель и отвечает ли помощник. Пока модель не скачана, помощник отвечает `unavailable` и показывает цифры, посчитанные системой.

## Настройки

| Переменная | Значение |
| --- | --- |
| `LLM_PROVIDER` | `external` (внешний сервис) или `ollama` (локальная модель) |
| `LLM_EXTERNAL_URL`, `LLM_EXTERNAL_MODEL`, `LLM_API_KEY` | адрес, имя модели и ключ внешнего сервиса. Ключ только в `.env`, не в Git |
| `OLLAMA_URL` | `http://ollama:11434` (имя сервиса в сети Compose) |
| `OLLAMA_MODEL` | `qwen2.5:7b` (выбрана по замерам на стенде, см. ниже); её же сервис `ollama` скачивает при старте |
| `OLLAMA_KEEP_ALIVE` | сколько `ollama` держит модель в памяти между вопросами (в compose по умолчанию `30m`) |
| `LLM_TIMEOUT_S` | таймаут ответа модели, секунды (по умолчанию 60) |

Все значения по умолчанию заданы в `compose.yaml`: пока остаёмся на `ollama`, `.env` стенда менять не нужно.

## Шаги

1. **Железо.** `qwen2.5:7b` занимает порядка 5 ГБ видеопамяти; на стенде (A10, 23 ГБ, рядом модуль `face` на 3–4 ГБ) она помещается и закреплена в памяти (`keep_alive: -1`). На CPU такая модель будет заметно медленнее. Меньшие `qwen2.5:3b` и `qwen2.5:1.5b` можно указать в `OLLAMA_MODEL`.

   **Замеры на стенде (10.10.2026, 8 вопросов, прогретая модель, A10, температура 0).** Все три модели прошли проверки на новых промптах. До правки промптов все три ошибочно отвечали «данных нет» на вопрос «кто вчера отработал меньше N часов», `1.5b` добавила несуществующий показатель («резервных смен»), `3b` и `7b` приписывали людям время ухода и выдумывали список последних отказов.

   | Модель | Выдуманные числа | Ложные `bad_response` | Задержка | Замечание |
   | --- | --- | --- | --- | --- |
   | `qwen2.5:1.5b` | 0 | 0 | 0,4–1,3 с | не говорит, какая зона максимальная, склонения хуже |
   | `qwen2.5:3b` | 0 | 0 | 0,6–3,0 с | нормальный русский, формулировки шаблонные |
   | `qwen2.5:7b` | 0 | 0 | 0,8–4,8 с | лучший русский и краткость; выбрана |

2. **Сервис `ollama`** уже в `compose.yaml`: образ `ollama/ollama:0.40.2`, закреплён по digest. Доступен только бэкенду: сеть `llm` (в ней только `backend` и `ollama`), без `ports:`. Сеть не `internal`, потому что при старте сервис скачивает модель с registry.ollama.ai. Образ не `read_only`: Ollama пишет в свой каталог. На стенде подключена видеокарта (общая с `face`), без неё модель считается на CPU. Бэкенд от `ollama` не зависит: пока модель скачивается, помощник отвечает `unavailable`, а остальная система и деплой работают.
3. **Модель скачивается сама.** Контейнер при старте запускает сервер и в фоне делает `ollama pull $OLLAMA_MODEL` (до 40 попыток с паузой 15 с, потом сдаётся). Веса лежат в томе `ollama_data` и переживают пересоздание контейнера; первая загрузка около 5 ГБ для `qwen2.5:7b`. Проверка: `docker compose exec ollama ollama list` (на стенде `deploy/dc exec ollama ollama list`). Если сеть была недоступна и скачивание сдалось: `docker compose restart ollama` или вручную `docker compose exec ollama ollama pull qwen2.5:7b`. Без интернета: перенести том `ollama_data` с машины, где модель уже скачана.
4. **Переключить.** По умолчанию уже `LLM_PROVIDER=ollama`. На стенде провайдер задаётся в `/srv/prohodnaya/.env`, затем деплой или `deploy/dc up -d backend` (бэкенд читает `.env` при создании контейнера). Кроме `.env`, в интерфейсе будет переключатель провайдера без правки файла: его делает другой участник через `PUT /api/assistant/provider`; здесь он не проверялся.
5. **Проверить.** В интерфейсе руководителя (`manager1`) задать вопрос «кто сейчас на объекте». Ответ должен прийти от локальной модели, числа совпадают с данными системы. Убедиться, что вызов не уходит наружу: `LLM_EXTERNAL_URL` и `LLM_API_KEY` можно оставить пустыми.
6. **Переключить на внешний сервис:** в `.env` стенда `LLM_PROVIDER=external`, `LLM_EXTERNAL_URL`, `LLM_EXTERNAL_MODEL`, `LLM_API_KEY` (ключ только в `.env`, не в Git), затем `deploy/dc up -d backend` (локально `docker compose up -d backend`). Сервис `ollama` продолжает работать; чтобы освободить видеокарту и память, остановите его: `deploy/dc stop ollama`. Вернуть локальную модель: `LLM_PROVIDER=ollama` и снова `up -d backend` (и `up -d ollama`, если останавливали).

## Если не работает

- Помощник отвечает «временно недоступен»: `ollama` не запущен, модель ещё скачивается или не скачалась, или неверен `OLLAMA_URL`. Проверить `docker compose ps ollama`, `docker compose logs --tail 50 ollama`, `docker compose exec ollama ollama list`. Остальная система при этом работает, ответ не выдумывается.
- Ответ не по формату или странный текст на маленькой модели: повторить вопрос. Числа в ответе берутся из данных системы, формулировка может быть хуже.
- Первый ответ долгий: модель загружается в память при первом запросе.

## Что изменится при переходе

- **Железо.** Нужна память под модель и процессорное время; внешнему сервису нужен только интернет.
- **Скорость.** Маленькая модель на CPU отвечает дольше, чем внешний сервис; цифры не измерялись.
- **Качество.** Формулировки у `qwen2.5:7b` хуже, чем у больших внешних моделей. Корректность чисел не зависит от модели: их считает система.
- **Стоимость.** Нет платы за запросы, есть стоимость железа и электричества.
- **Приватность.** При `ollama` вопрос и факты остаются внутри стенда. При `external` они уходят внешнему провайдеру; фото и эмбеддинги лиц помощнику не передаются по замыслу (проверить по коду слоя после слияния). Распознавание лиц в любом режиме локальное.
