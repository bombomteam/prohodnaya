# Переход на локальную модель

Для помощника руководителя. Провайдер выбирается настройкой, код менять не нужно. Состояние на 10.10.2026: слой `backend/app/llm/` и провайдеры делаются параллельно и в `main` пока только как интерфейс; сервиса `ollama` в `compose.yaml` нет. Шаги ниже описывают целевое состояние. **Не проверено:** ни один шаг с `ollama` в этом репозитории ещё не прогонялся. После слияния ветки помощника сверьте имена переменных с `.env.example`.

## Настройки

| Переменная | Значение |
| --- | --- |
| `LLM_PROVIDER` | `external` (внешний сервис) или `ollama` (локальная модель) |
| `LLM_EXTERNAL_URL`, `LLM_EXTERNAL_MODEL`, `LLM_API_KEY` | адрес, имя модели и ключ внешнего сервиса. Ключ только в `.env`, не в Git |
| `OLLAMA_URL` | `http://ollama:11434` (имя сервиса в сети Compose) |
| `OLLAMA_MODEL` | `qwen2.5:1.5b` |

## Шаги

1. **Железо.** `qwen2.5:1.5b` маленькая модель: порядка 1–2 ГБ памяти, запускается на CPU (оценка, не измерено). На стенде видеокарта A10 общая с `face` (бюджет модуля лиц `FACE_GPU_MEM_MB=2048`), поэтому для показа берём CPU или небольшую долю GPU. Модель побольше можно указать в `OLLAMA_MODEL`; качество и скорость не проверялись.
2. **Сервис `ollama`.** Его нужно добавить в `compose.yaml`, а это папка DevOps. Просьба DevOps (черновик, не проверен):

   ```yaml
   ollama:
     image: ollama/ollama:<закрепить версию>
     profiles: [backend]
     restart: unless-stopped
     volumes:
       - ollama_data:/root/.ollama      # веса модели переживают перезапуск
     networks: [edge]                   # без ports: доступен только бэкенду по http://ollama:11434
   # в volumes: добавить ollama_data: {}
   ```

   Образ не `read_only`: Ollama пишет в свой каталог. GPU при необходимости пробрасывается так же, как для `face` (`deploy/compose.stand.yaml`).
3. **Скачать модель один раз** (нужен интернет): `docker compose exec ollama ollama pull qwen2.5:1.5b`. Проверка: `docker compose exec ollama ollama list`. Без интернета: перенести том `ollama_data` с машины, где модель уже скачана.
4. **Переключить.** В `.env`: `LLM_PROVIDER=ollama`, `OLLAMA_URL=http://ollama:11434`, `OLLAMA_MODEL=qwen2.5:1.5b`. Пересоздать бэкенд, чтобы он перечитал `.env`: `docker compose up -d backend`. На стенде это делает DevOps: правка `/srv/prohodnaya/.env`, затем `deploy/dc up -d backend`.
5. **Проверить.** В интерфейсе руководителя (`manager1`) задать вопрос «кто сейчас на объекте». Ответ должен прийти от локальной модели, числа совпадают с данными системы. Убедиться, что вызов не уходит наружу: `LLM_EXTERNAL_URL` и `LLM_API_KEY` можно оставить пустыми.
6. **Вернуться** к внешнему сервису: `LLM_PROVIDER=external`, заполнить `LLM_EXTERNAL_URL`, `LLM_EXTERNAL_MODEL`, `LLM_API_KEY`, снова `docker compose up -d backend`.

## Если не работает

- Помощник отвечает «временно недоступен»: `ollama` не запущен, модель не скачана или неверен `OLLAMA_URL`. Проверить `docker compose ps ollama`, `docker compose logs --tail 50 ollama`, `ollama list`. Остальная система при этом работает, ответ не выдумывается.
- Ответ не по формату или странный текст на маленькой модели: повторить вопрос. Числа в ответе берутся из данных системы, формулировка может быть хуже.
- Первый ответ долгий: модель загружается в память при первом запросе.

## Что изменится при переходе

- **Железо.** Нужна память под модель и процессорное время; внешнему сервису нужен только интернет.
- **Скорость.** Маленькая модель на CPU отвечает дольше, чем внешний сервис; цифры не измерялись.
- **Качество.** Формулировки у `qwen2.5:1.5b` хуже, чем у больших внешних моделей. Корректность чисел не зависит от модели: их считает система.
- **Стоимость.** Нет платы за запросы, есть стоимость железа и электричества.
- **Приватность.** При `ollama` вопрос и факты остаются внутри стенда. При `external` они уходят внешнему провайдеру; фото и эмбеддинги лиц помощнику не передаются по замыслу (проверить по коду слоя после слияния). Распознавание лиц в любом режиме локальное.
