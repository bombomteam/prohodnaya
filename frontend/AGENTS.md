# Фронтенд «Проходной»: инструкции для ИИ-ассистента

Прочитай этот файл целиком перед любой правкой в `frontend/`. Общие правила проекта — в [корневом AGENTS.md](../AGENTS.md), контракт с бэкендом — в [docs/frontend-api.md](docs/frontend-api.md).

## Что это и как устроено

- Статическое браузерное приложение на чистых ES-модулях, **без npm-зависимостей, без сборщика и без фреймворка**. Четыре роли: администратор, контролёр (проходная), рабочий (телефон), руководитель.
- `index.html`, `styles.css` — разметка и стили; `src/app.js` — интерфейс; `src/api.js` — **все** HTTP-запросы к бэкенду; `src/demo-api.js` — деморежим (данные в `localStorage`); `src/webauthn.js` — привязка и подтверждение телефона.
- `config.js` задаёт режим: `demo` (без сервера) или `api` (с бэкендом, адрес — `apiBaseUrl`). В Docker-контейнере этот файл **не используется из репозитория**: контейнер генерирует его при старте из переменных окружения. Правка `frontend/config.js` влияет только на локальный запуск через `python -m http.server` и на GitHub Pages.
- Бэкенда пока нет. Деморежим не доказывает безопасность прохода — не подавай его как готовую серверную проверку.

## Инфраструктура (уже сделано, не переделывай)

| Где | Что | Как обновляется |
| --- | --- | --- |
| GitHub Pages — https://bombomteam.github.io/prohodnaya/ | Демо из `main` | Автоматически при push в `main` (`.github/workflows/pages.yml`: `npm test` → `npm run build:pages` → публикация) |
| GitHub Packages — `ghcr.io/bombomteam/prohodnaya-frontend` | Docker-образ, теги `latest` и хеш коммита | Автоматически при push в `main` с изменениями в `frontend/` (`.github/workflows/frontend-image.yml`: тесты → сборка → проверка контейнера → публикация) |
| Стенд на сервере — http://195.209.220.254 | Контейнер из `compose.yaml` в корне репо | **Пока вручную**, это делает ответственный за инфраструктуру. Автодеплой на сервер ещё не настроен |

Контейнер запущен с жёсткими ограничениями. Код должен с ними работать:

- **Файловая система только для чтения.** Писать можно только в `/tmp`. Приложение статическое, поэтому обычно это не мешает.
- **Статика отдаётся только на GET и HEAD.** POST и другие методы на страницы фронта получают 403. Формы отправляются через `fetch` в API (`/api/...`), а не обычным `<form method="post">`.
- **Заголовки безопасности** (`frontend/docker/security-headers.conf`):
  - `X-Frame-Options: DENY`: приложение нельзя встроить в `<iframe>`;
  - `Permissions-Policy` разрешает только камеру, геолокацию и WebAuthn, а микрофон, платежи и USB заблокированы. Если нужен новый API браузера, его не будет. Скажи об этом человеку, сам не меняй.
- **Внешние ресурсы:** сейчас подключён только Google Fonts. Новые CDN не добавляй: на защите может не быть интернета, а приватность данных важна по кейсу.
- **Камера, WebAuthn и геолокация работают только на `localhost` или по HTTPS.** Стенд пока на HTTP, поэтому на телефоне эти функции там не заработают. Это известное ограничение, обходить его в коде не надо.

## Границы: что можно, что нельзя

Можно свободно менять: `index.html`, `styles.css`, `src/*.js`, `tests/`, `docs/`, `config.js` (только `mode` и `apiBaseUrl`).

**Не трогай без прямой просьбы человека**:

- `compose.yaml`, `.env.example`;
- `.github/workflows/*`;
- `frontend/Dockerfile`, `frontend/docker/*`;
- `face/` (модуль распознавания лиц, его ведёт ответственный за инфраструктуру).

Если правка в них кажется нужной, остановись и опиши человеку, что и зачем менять. Он согласует это с ответственным за инфраструктуру.

**Не делай:**

- не добавляй npm-пакеты, сборщики (Vite, Webpack), React или TypeScript и не переписывай приложение на другой стек;
- не создавай свои Dockerfile, compose-файлы, nginx-конфиги, workflow и скрипты деплоя;
- не пиши в `config.js` секреты, токены и ключи: браузер видит этот файл целиком;
- не вписывай адрес API в код, используй `config.apiBaseUrl`;
- не делай HTTP-запросы мимо `src/api.js`;
- не принимай на фронте решения, которые должен принимать сервер (пропуск, сравнение лица, итоговые цифры отчётов).

## Ловушка: новые файлы

`scripts/build-pages.mjs` копирует на GitHub Pages **только явный список**: `index.html`, `styles.css`, `config.js` и четыре модуля `src/app.js`, `src/api.js`, `src/demo-api.js`, `src/webauthn.js`. Docker-образ при этом копирует всю папку `src/`.

- **Новый файл в `src/`:** добавь его имя в список модулей в `scripts/build-pages.mjs`. Иначе в Docker всё заработает, а Pages сломается.
- **Новый файл в корне `frontend/`** (картинка, шрифт, манифест): лучше положи его в `src/`. Если нужен именно в корне, это требует правки `Dockerfile`. Скажи об этом человеку.

## Проверка перед push (обязательно)

Из папки `frontend`:

```powershell
npm test
npm run build:pages
```

Оба шага должны пройти без ошибок. Если ты менял что-то, что затрагивает работу в контейнере, проверь и его (см. «Локальная работа», шаг 4). Не сообщай, что проверка пройдена, если ты её не запускал.

## Git

- Перед началом работы и перед push: `git pull --rebase`.
- Коммить маленькими осмысленными шагами, сообщение в стиле репозитория: `feat(frontend): ...`, `fix(frontend): ...`, `docs(frontend): ...`.
- Никогда не делай `git push --force`, не переписывай чужие коммиты, не коммить `.env`, `node_modules/`, `dist/`.
- Коммит делается от имени человека, который работает. Не подставляй чужое имя.

## Что происходит после push в `main`

1. Запускаются оба workflow (см. таблицу выше). Результат виден на вкладке **Actions** репозитория.
2. Если что-то красное, исправь и запушь снова. Красный `main` мешает всей команде.
3. Стенд на сервере сам **не** обновится. Скажи человеку, что изменения готовы для выкладки на стенд.

## Локальная работа (Windows, PowerShell)

1. **Получить свежий код:** `git pull --rebase`.
2. **Быстрая разработка** (нужен Python 3):
   ```powershell
   cd frontend
   python -m http.server 8080
   ```
   Откройте http://localhost:8080. Это деморежим, после правки достаточно обновить страницу. Через `file://` не открывать.
3. **Тесты** (нужен Node.js 22+):
   ```powershell
   cd frontend
   npm test
   npm run build:pages
   ```
4. **Проверка «как на сервере»** (нужен Docker Desktop). Запускается из корня репозитория:
   ```powershell
   Copy-Item .env.example .env
   ```
   В `.env` поставьте `FRONTEND_PORT=8080`, потому что порт 80 на Windows часто занят. Затем:
   ```powershell
   docker compose up -d --build
   ```
   Откройте http://localhost:8080. Если тут всё работает, на сервере тоже заработает: там тот же контейнер с теми же ограничениями. Остановить:
   ```powershell
   docker compose down
   ```
5. **Закоммитить и запушить:** `git add <файлы>`, `git commit -m "feat(frontend): ..."`, `git pull --rebase`, `git push`.
