# Телефон рабочего и подтверждение прохода

## Вход рабочего

Рабочий открывает `/?worker=1`, на стенде — `https://hack-detect.duckdns.org/?worker=1`.
Также поддерживается ссылка активации `/enroll?code=…`. Вход в Keycloak рабочему не нужен:
профиль в API-режиме определяется зарегистрированным ECDSA-ключом устройства.
На операторских экранах добавлена ссылка «Открыть телефон рабочего».

## Новый сценарий: реализован в деморежиме

1. Контролёр выбирает сотрудника по ФИО или ID пропуска и направление вход/выход.
2. Отправляет запрос выбранному сотруднику. Код на экране контролёра не показывается.
3. В профиле рабочего появляется запрос. Кнопка «Я на проходной — получить код» подтверждает участие рабочего.
4. Рабочий видит шестизначный код и называет его контролёру.
5. Контролёр вводит код. После его проверки доступны камера и отправка снимков.
6. Система проверяет лицо; только итоговое разрешение открывает или закрывает смену.
7. Код исчезает после потребления, отмены новым запросом или истечения срока.

Демо работает в двух вкладках одного браузерного профиля с общим `localStorage`.
Выбор рабочего в демопрофиле имитирует устройство и не является авторизацией.
Разные телефоны должны обмениваться через сервер. SMS и push-уведомления не реализованы.
Коды и решения деморежима имитируются; этот прогон не доказывает защищённость прохода.

Для проверки: в первой вкладке выберите демо-роль `controller`, сотрудника Тимур Соколов и отправьте запрос.
Во второй откройте `/?worker=1`, выберите Тимура и получите код. Вернитесь в первую,
введите код, снимите лицо и отправьте проверку. Вторая вкладка обновляет профиль автоматически.

## Подключение к бэкенду: ожидается согласованный контракт

В проверенной ветке `origin/feature/svyat` (`dd73838`) есть прежний обмен QR/подписью:
`POST /passages` принимает только направление, телефон вводит QR и вызывает `/sign`.
В API-режиме этот существующий обмен сохранён. Новый шестизначный сценарий пока включён
только для демо; несуществующие HTTP-маршруты фронт не вызывает.
Команда сообщила, что контракт уже согласован и будет передан отдельно.

Для адаптера нужны точные маршруты, JSON и авторизация следующих операций:

- Поиск доступных контролёру сотрудников по пропуску; административный `/persons` для этого не подходит по роли.
- Создание запроса с привязкой к конкретному человеку и направлению.
- Получение собственных ожидающих запросов с телефона; сервер идентифицирует телефон по ключу, а не доверяет `person_id` из браузера.
- Подтверждение конкретной попытки подписью телефона и получение шестизначного кода в его профиль.
- Ввод и проверка кода контролёром, срок действия, ограничения перебора и повторного использования.
- Статус своей смены и окончательного решения для телефона.

Сохранить связь подтверждения с попыткой, nonce, человеком и направлением.
Код проверяется сервером совместно с подписью телефона и сравнением лица 1:1.
Проверка кода сама по себе не открывает смену. Сервер записывает отказы в журнал.
Технические ошибки содержат `message`; итоговый отказ — `decision: "deny"` с человеческой причиной.

## Камера и причины отказов

- Запасной режим браузера: `facingMode: "environment"`, желаемые 1280×720,
  три кадра с интервалом 250 мс, JPEG 0.88, исходные размеры, без зеркалирования.
- HTTP-адаптер допускает 1–10 кадров; интерфейс снимает три.
- `/face` использует Bearer-токен контролёра. Таймаут — 35 секунд.
- Для решения и журнала показывается `reason.text`; поддержаны `message` и прежняя строка `reason`.
- Живой просмотр открывается отдельной вкладкой:
  `https://console.195-209-220-254.sslip.io/console/`. Доступ выдаёт владелец камеры.

## Проверки

`npm test` проверяет целевой профиль, чужой телефон, неверный код, необходимость подтверждения,
камеры и одноразового использования, вход/выход, смены и геолокацию.
`npm run build:pages` создаёт статический артефакт.

Дополнительный браузерный прогон: `node scripts/worker-flow.cdp.mjs`.
Нужны локальный demo-сайт и отдельный тестовый профиль Edge/Chrome с CDP и тестовой камерой
(параметры в начале скрипта). Скрипт добавляет тестового рабочего в локальное демо.
Он проходит путь в двух вкладках и проверяет ширины 320/390/768/1280 px.
Физическая камера, настоящий ключ телефона и сравнение лица на сервере требуют отдельной проверки после интеграции.
