# Интеграция фронтенда с `feature/svyat`

Актуально для маршрутов и схем backend, слитого в `main` из `feature/svyat`, включая обновление модуля лиц в merge `c20b66c`. Все пути ниже имеют префикс `/api`; базовый URL задаётся `config.apiBaseUrl` либо переменной контейнера. Фронтенд хранит HTTP-адаптер в `src/api.js` и не принимает решение о проходе.

## Роли и вход

- `admin`: сотрудники, группы, журнал, присутствующие.
- `controller`: создание прохода, опрос сессии, отправка кадров.
- `manager`: присутствующие, журнал, план, зоны, аналитика, отчёт, помощник.
- `worker`: привязка устройства, подпись прохода, отправка координат без операторского токена.

Backend защищает операторские маршруты Bearer JWT Keycloak. В этой ветке нет `/auth/config`, `/auth/exchange`, `/auth/refresh`, `/auth/logout`, которые использует браузерный PKCE-клиент. Поэтому обычный вход оператора до их реализации не работает. Для локальной проверки API можно открыть `http://localhost:8080/?devRole=admin`, `manager` или `controller` при `AUTH_DEV_BYPASS=true` на backend. Этот режим ограничен браузерным localhost; сервер должен отдельно включить bypass. Рабочий открывает `?worker=1`.

Точный контракт для реализации `/auth/*` — [задание бэкендеру](backend-auth-handoff.md). Redirect URI всегда `location.origin + "/"`; на стенде это `https://hack-detect.duckdns.org/`, Keycloak — `https://auth.hack-detect.duckdns.org`. Клиент `panel` должен иметь default scopes `basic`, `acr` и audience `access-api`. Уже импортированный realm обновляет владелец стенда после слияния PR.

## Администратор

- `GET /groups`, `POST /groups` (`name`, `parent_id`), `GET /persons`: группы и таблица; `PersonOut` содержит `fio`, `position`, `group`, `status`, `on_site`, `has_face`, `has_active_device`.
- `POST /persons`, `PATCH /persons/{id}`: multipart с `fio`, `position`, `group_id`, `photo`; для создания фото обязательно.
- Отказ проверки фото приходит как HTTP-ошибка `{code:"FACE_<ПРИЧИНА>",message:"Текст для человека"}`. Интерфейс показывает `message` прямо в форме сотрудника, сохраняет введённые поля и выбранный файл; код остаётся в `ApiError.code`. Недоступность модуля лиц — `503 / FACE_SERVICE_UNAVAILABLE`. Запись сотрудника при отказе проверки не создаётся.
- `POST /persons/{id}/enroll-code`: выдаёт `code`, `enroll_url`, `expires_at`.
- `PATCH /persons/{id}` со `status=blocked`: блокировка. Маршрута отзыва конкретного устройства пока нет.
- `GET /events`: журнал попыток. `GET /site/now`: присутствующие; сервер пока не даёт общего количества людей и числа отказов за сегодня.

## Проходная и телефон

Сценарий API-режима совпадает с демо: «контролёр выбирает человека → рабочий нажимает на телефоне «Я на проходной — получить код» → контролёр вводит шесть цифр → кадры лица → решение сервера».
Подробности и границы готовности — [телефон и проход](worker-passage.md).

1. Контролёр (`controller`): `GET /passages/people?q=&limit=50` — поиск по ФИО (`id`, `fio`, `position`, `group`, `status`, `on_site`, `has_face`, `has_active_device`). При вводе в поиск фронт повторяет запрос с `q` (задержка 300 мс).
2. `POST /passages` с `{person_id, direction:"in"|"out"}` создаёт сессию: `session_id`, `status` (`pending`|`signed`|`decided`), `expires_at`, `person`, `decision`, `reason_code`, `reason`, `code_delivered`. Код в ответе никогда не приходит. Отказ по правилам (заблокирован, уже на объекте, нет смены, нет эталона, нет телефона) приходит сразу как `status:"decided"`, `decision:"deny"` с причиной: фронт показывает его как результат без камеры.
3. Рабочий передаёт открытый JWK через `POST /enroll` с кодом (`code`, `public_key_jwk`). Закрытый ECDSA P-256 ключ остаётся в IndexedDB как неизвлекаемый `CryptoKey`.
4. Телефон по кнопке вызывает `POST /device/pass-code` без токена: `{device_id, ts, signature}`, где `ts` — ISO 8601 с часовым поясом (`new Date().toISOString()`), подпись ECDSA SHA-256 над UTF-8 строкой `pass-code|<device_id>|<ts>`, raw `r||s` в base64url без padding. Ответ `{pending:false}` — «Контролёр ещё не создал проход для вас»; `{pending:true, session_id, direction, code, expires_at}` — крупно показываются шесть цифр и срок. Автоопроса нет: каждый вызов — осознанное нажатие рабочего («Проверить снова»). Ошибки: `403 DEVICE_INVALID`, `409 STALE_REQUEST` (часы телефона), `409 REPLAYED`.
5. Контролёр вводит цифры: `POST /passages/{id}/code` `{code}` (6 цифр). Верный код — `status:"signed"`. Неверный — HTTP 200, сессия остаётся `pending`, в ответе `reason_code:"CODE_INVALID"` и `reason` с числом оставшихся попыток: фронт показывает это ошибкой и оставляет форму. Исчерпание попыток или отзыв телефона — `status:"decided"`, `decision:"deny"`.
6. Затем камера контролёра снимает три JPEG-кадра с интервалом 300 мс (задняя камера, 0.88, без зеркалирования) и отправляет multipart-полем `frames` в `POST /passages/{id}/face`. HTTP-адаптер допускает 1–10 кадров. Все запросы контролёра используют `Authorization: Bearer <access token>` с ролью `controller`; подпись рабочего этот токен не заменяет. Локальный `devRole=controller` работает без токена только при серверном `AUTH_DEV_BYPASS=true`. Решение `allow`/`deny` приходит только от сервера; 401/403 показываются как ошибки сессии/прав. `GET /passages/{id}` опрашивается раз в 2 секунды, пока сессия ждёт или код принят.
7. Рабочий отправляет `POST /locations`: `device_id`, точная JSON-строка `payload` с `ts` и `points[{ts,lat,lon,accuracy}]`, а также ECDSA-подпись точных байтов этой строки. Сервер отвечает `accepted`/`rejected`.

В backend нет маршрута статуса смены для телефона: на экране рабочего написано «Статус смены видит контролёр». Сервер ограничивает приём геолокации открытой сменой. Не реализованы идемпотентность регистрации/прохода и восстановление ключа после сбоя ответа.

Технические отказы: `404 SESSION_NOT_FOUND`, `404 PERSON_NOT_FOUND`, `403 DEVICE_INVALID`, `409 SESSION_EXPIRED`, `403 SESSION_FOREIGN` (сессию ведёт только создавший её контролёр). Фронт сохраняет HTTP-статус и `code`, показывает серверный `message`, в том числе при 403. Общие сообщения 401/403 используются только при отсутствии текста сервера. Отказ по правилам — HTTP 200 с `decision: "deny"`, показывается как результат прохода. Проверка лица и сохранение эталона ждут до 35 секунд (`config.faceRequestTimeoutMs`), чтобы успеть получить ответ прокси с таймаутом 30 секунд; остальные запросы — 15 секунд (`config.requestTimeoutMs`). Автоматического повтора прохода нет.

`/enroll?code=…` обслуживается контейнером фронта как экран рабочего; код заполняется в форме и удаляется из адресной строки. `/enroll/` перенаправляется на `/enroll` с сохранением query. Для локального статического сервера без этого маршрута используйте `/?worker=1&code=…`.

## Руководитель

- `GET /site/plan`: размеры изображения, калибровка и многоугольники зон в пикселях. `PUT /site/plan` принимает `image`; `PUT /site/calibration` принимает ровно три точки `{px,py,lat,lon}`; `PUT /zones` заменяет список зон `{name,polygon}`.
- `GET /analytics/heatmap` и `/analytics/routes`: фильтры `from`, `to`, `hour_from`, `hour_to`, `person_ids`. Тепловая карта считает минуты по зонам, маршруты используют пиксельные `x,y`.
- `GET /reports/person/{id}?from&to`: табель конкретного сотрудника. Общего `/reports/shifts` нет. Список для выбора составляется из `/site/now` и людей с маршрутом за выбранный период; отдельного списка всех людей для роли manager API не даёт.
- `POST /assistant/ask` с `question`; `POST /assistant/summary` с `date_from`, `date_to`. Ответ `{status,text,facts_used}`.

`image_url` текущего stub-плана равен `/files/plan/plan.png`, но маршрута файла в backend нет. Интерфейс показывает только три зоны из материалов кейса: Бетономешалка, Котлован, Курилка. «Место для курения» в ответе API нормализуется в «Курилка»; прочие названия зон не включаются в схему и посещаемость. Фотографии зон лежат в `src/assets/`. По ФИО открывается карта перемещений выбранного работника и хронология точек; зона определяется по `zone_id`, неизвестная или отсутствующая зона помечается «Вне трёх заданных зон». Без серверного плана и полигонов блоки трёх зон условные. План с контурами и точками отображается после появления доступного изображения, размеров, трёх полигонов и координат маршрута `x,y`. Деморежим не относит новые GPS-координаты к зоне без калибровки.

## Статус backend

Маршруты, Pydantic-схемы и миграция БД слиты в `main`. Последующие изменения реализовали хранение людей и групп, проверку эталона через `face.analyze` и активацию телефона. Проход по коду (`/passages/*`, `/device/pass-code`), смены, координаты и аналитика реализованы на сервере; сверка фронта с маршрутами выполнена 2026-10-10 по `backend/app/api`. Совпадение HTTP-контракта не доказывает безопасность допуска: решение о проходе принимает только сервер, а сквозную работу на стенде (камера, реальный ключ телефона, сравнение лица) нужно проверять отдельно.
