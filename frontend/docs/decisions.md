# Решения по фронтенду

## 1. Статический JavaScript без сборщика

**Варианты:** React/Vite или HTML/CSS/ES-модули. **Выбор:** ES-модули без зависимостей, чтобы за время кейса быстро запустить интерфейсы на чистой машине. **Риск:** крупный `app.js` сложнее поддерживать; при росте проекта его следует разделить по экранам.

## 2. Один API-адаптер и явно отделённое демо

**Варианты:** запросы прямо из экранов или единый `api.js`. **Выбор:** единый адаптер с отдельным `demo-api.js`, чтобы серверный контракт можно было изменить в одном месте. **Риск:** демо может выглядеть убедительно, хотя не проверяет безопасность; поэтому каждый экран помечен предупреждением, а сборка Pages допускает только деморежим.

## 3. Одноразовый запрос + WebAuthn + снимок

**Варианты:** статический QR/код, одноразовый код без ключа устройства, WebAuthn. **Выбор:** UI готов к WebAuthn: короткий код связывает экран рабочего с конкретной попыткой, подпись ключа подтверждает устройство, камера передаёт лицо. **Риск:** защита зависит от серверной проверки всей цепочки и от доверенной регистрации устройства; сервер ещё не реализован, поэтому свойство «нельзя пройти за другого» пока не достигнуто.

## 4. Сетка зон 3 × 3 и метрика точек

**Варианты:** произвольные полигоны или фиксированная сетка. **Выбор:** девять зон с настраиваемыми границами координат и названиями, одна понятная метрика — количество принятых точек в зоне. **Риск:** предоставленные снимки площадки не дают точной географической привязки; схема и границы должны быть откалиброваны с командой. Число точек не равно времени пребывания.

## 5. GitHub Pages публикует только фронт

**Варианты:** публикация всего репозитория или отдельного статического артефакта. **Выбор:** workflow загружает только `frontend/dist/pages/`. **Риск:** GitHub Pages не запускает сервер кейса; опубликованная версия остаётся демонстрацией интерфейса до отдельного развёртывания бэкенда.
